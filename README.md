# ПРОСТОР MVP — ИИ-агент умного поиска + умный конструктор ТЗ

Прототип по двум кейсам хакатона в одном приложении с общей навигацией:

* **Кейс 2 — ИИ-агент умного поиска.** Запрос на естественном языке → релевантные услуги
  с обоснованием → аналогичные выполненные работы → исполнители с обоснованием →
  связанные услуги → черновик заявки.
* **Кейс 1 — умный конструктор ТЗ.** Сборка документа из типовых блоков, автоматическая
  структура по типу ТЗ, процент готовности, риски и рекомендации, выгрузка
  `.docx` и `.pdf`.
* **Интеграция кейсов.** Кнопка «Сформировать ТЗ» переносит услугу, этапы, сроки,
  исполнителей и условия работ из диалога в конструктор — заполнять заново ничего не нужно.

Всё построено на реальной выгрузке из ПРОСТОР: 51 услуга, 13 компаний, 20 договоров,
462 расчёта, 1676 этапов работ, 318 операций, 673 расценки.

## Быстрый старт

```bash
docker compose up --build          # ~3 минуты на первую сборку
```

| Что | Адрес |
|---|---|
| Приложение | http://localhost:3000 |
| Chat Service (агент, каталог, аналитика) | http://localhost:8080 |
| TZ Generator (шаблоны, черновики, документы) | http://localhost:8081 |
| MinIO console | http://localhost:9001 (`minioadmin` / `minioadmin`) |
| PostgreSQL | `localhost:5432`, `prostor` / `prostor` |

Логин/пароль БД и MinIO — значения по умолчанию для локального прототипа,
заданы в `docker-compose.yml` через `${POSTGRES_USER:-prostor}` и подобные
подстановки. Переопределяются через `.env` (см. `.env.example`), в самом
compose-файле никаких кредов не захардкожено.

База инициализируется автоматически: схема → шаблоны ТЗ → данные выгрузки → функции поиска —
это скрипты `db/init/*.sql`, которые официальный образ Postgres выполняет по алфавиту
через `docker-entrypoint-initdb.d`, но **только когда `pgdata` volume пустой** (это разовый
bootstrap, а не система миграций). Если вы уже поднимали проект и меняете `db/init`,
пересоздайте volume: `docker compose down -v && docker compose up --build`. Эмбеддинги
каталога считает фоновый индексатор внутри Chat Service, это занимает несколько секунд
после старта.

**Смена модели эмбеддингов требует переиндексации.** Индексатор заполняет только строки
с `embedding IS NULL`, поэтому после перехода с заглушки на bge-m3 (или между моделями)
старые векторы останутся несовместимыми с новыми запросами — поиск не упадёт, а тихо
начнёт выдавать ерунду. Покрытие индекса видно в `GET /health` (`index.ready`), сброс:

```bash
docker compose exec -T db psql -U prostor -d prostor -c \
  "UPDATE search.product_chunk SET embedding = NULL;
   UPDATE search.company_chunk SET embedding = NULL;
   TRUNCATE search.embedding_cache;"
docker compose restart chat
```

Скрипты `06_document_versions.sql`, `07_document_status.sql`, `08_review.sql` и
`09_review_seed.sql` идемпотентны и накатываются на уже поднятую базу без
пересоздания volume (команда — в шапке каждого файла), например:

```bash
docker compose exec -T db psql -U prostor -d prostor -v ON_ERROR_STOP=1 \
  -f /docker-entrypoint-initdb.d/08_review.sql
docker compose exec -T db psql -U prostor -d prostor -v ON_ERROR_STOP=1 \
  -f /docker-entrypoint-initdb.d/09_review_seed.sql
```

`09_review_seed.sql` кладёт четыре демо-ТЗ, уже направленных подрядчикам NNG,
GTP и ORB, — чтобы вход под ролью подрядчика не был пустым экраном.

Правки в `db/init/04_functions.sql` накатываются на живую базу без пересоздания volume —
все функции там пересоздаются идемпотентно:

```bash
docker compose exec -T db psql -U prostor -d prostor -v ON_ERROR_STOP=1 \
  -f /docker-entrypoint-initdb.d/04_functions.sql
```

**Ключи моделей не обязательны.** Без `LLM_API_KEY` чат отвечает шаблонным «стенографом»;
без `EMBEDDING_BASE_URL` каталог индексируется детерминированной заглушкой (hashing trick).
Переключаются независимо друг от друга, сценарий целиком проходит и без внешних вызовов.
Исключение — экстракция полей ТЗ из диалога (кнопка «Генерация технического задания
на основании диалога»): она осмысленна только с реальной моделью, на заглушке
возвращает пустой результат. Для провайдеров со Structured Outputs (OpenAI, vLLM)
можно включить строгую JSON-схему: `LLM_STRUCTURED_OUTPUTS=true` (для DeepSeek —
оставить `false`, см. `.env.example`).
LLM и эмбеддинги — разные endpoint'ы, каждый может быть любым OpenAI-совместимым сервисом:

```bash
# LLM: DeepSeek (или любой другой OpenAI-совместимый chat/completions)
LLM_API_KEY=sk-... LLM_BASE_URL=https://api.deepseek.com LLM_MODEL=deepseek-v4-flash \
# Эмбеддинги: bge-m3 через локальный Ollama (`ollama pull bge-m3`), хост виден
# из контейнера как host.docker.internal — ключ не нужен
EMBEDDING_BASE_URL=http://host.docker.internal:11434/v1 EMBEDDING_MODEL=bge-m3 \
docker compose up --build
```

Проще один раз положить эти переменные в `.env` (см. `.env.example`) — docker compose
подхватит его автоматически.

## Демо-сценарий за 90 секунд

1. Открыть http://localhost:3000, вкладка **ИИ-агент поиска**.
2. Написать «Нужно оценить запасы по объекту» — придёт текст от агента и карточки услуг
   с рангом, релевантностью и обоснованием подбора.
3. Выбрать услугу — появятся: датапикер с подсказкой типового срока, аналогичные
   выполненные работы, связанные услуги и рекомендации по заполнению заявки.
4. Указать период — придёт список исполнителей с рангом, опытом по этой услуге,
   загрузкой в заданном периоде и объяснением, почему именно они.
5. Выбрать исполнителей → отметить этапы работ (собраны из реальных расчётов) →
   в чате появится готовность ТЗ с рисками.
6. Нажать **«Генерация технического задания на основании диалога»** — агент
   разберёт всю переписку и предложит значения текстовых полей ТЗ (цель,
   периметр, исходные данные, объект…); каждое поле принимается отдельно.
   Работает только при заданном `LLM_API_KEY`.
7. Нажать **«Сформировать ТЗ в конструкторе»** — откроется Кейс 1 с предзаполненными полями.
8. В конструкторе: включить «Построение 3D геологической модели» — появится риск
   «выбрана 3D-модель без этапа подготовки исходных данных». Стереть объект работ —
   готовность упадёт, кнопка выгрузки заблокируется.
9. Заполнить недостающее → **«Сформировать документ»** → зона готового документа:
   предпросмотр, скачивание `.docx` или `.pdf` и переход в «Мои заявки» сразу на
   этот документ.
10. Переключить роль справа сверху с **НТЦ** на компанию-подрядчика — откроются
    **Входящие ТЗ** этой компании. Открыть направленное ТЗ, повесить замечание
    на раздел, нажать **«На доработку»** с причиной.
11. Вернуть роль **НТЦ** → «Мои заявки». Список разложен по категориям:
    «Черновики», «Готовы к отправке», «На согласовании», «Вернули с замечаниями»,
    «Согласованы» — со счётчиками. В категории «Вернули с замечаниями» у документа
    видны замечания подрядчика и кнопка **«Исправить раздел»**, которая открывает
    конструктор сразу на нужных полях. После правок — новая версия и повторное
    направление.
12. Вкладка **Аналитика** — витрины по обоим кейсам плюс согласование ТЗ.

## Архитектура

```
React (nginx)
  │  POST /turns (SSE) или один WebSocket на сессию — оба ведут в один и тот же обработчик хода
  ▼
Chat Service (C#)            ──синхронный HTTP──▶   TZ Generator (C#)
  slot filling, поиск, ранжирование                  готовность, риски, docx
  │            │                                      │            │
  ▼            ▼                                      ▼            ▼
PostgreSQL  pgvector                             PostgreSQL     MinIO S3
```

Ни брокера, ни outbox, ни Redis — обоснование в [`docs/architecture.md`](docs/architecture.md).
WebSocket есть, но не про server push: сервер по-прежнему ничего не инициирует
вне хода пользователя, сокет — это просто один канал на сессию вместо нового
HTTP-соединения на каждый ход. Оба транспорта (SSE и WebSocket) вызывают одно и
то же тело обработчика хода и одинаково защищены `Idempotency-Key`.

### Один ход диалога

| Вход | Эмбеддинг | SQL | LLM |
|---|---|---|---|
| Свободный текст | 0 или 1 вызов (только если решено искать; 0 при попадании в кэш) | 0–2 запроса | 1 вызов (разговор) или 2 (поиск) |
| Клик по карточке | 0 | 1 запрос | 0 |

Свободный текст обрабатывает один структурированный вызов модели — «мозг диалога»
(`backend/src/Prostor.Chat/Brain.cs`). За один round-trip он возвращает JSON, в
котором сразу всё: ответ пользователю, намерение хода (разговор / поиск услуг /
поиск исполнителей / выбор варианта из показанного списка / начать заново),
вытащенные из разговора данные для ТЗ, уместная следующая карточка и 2–4
подсказки следующей реплики. Подробности — в
[`docs/architecture.md`](docs/architecture.md#21-ход-диалога).

Что это даёт в диалоге:

- **разговор не обязан быть поиском.** На вопрос, сомнение, приветствие или
  «а как у вас всё устроено» приходит осмысленный ответ по контексту заявки, а не
  одна и та же заготовка;
- **карточки предлагаются, а не навязываются.** Список услуг, сроки, исполнители,
  этапы появляются в ленте, когда это уместно, и их можно проигнорировать — то же
  самое говорится словами: «давай первый вариант», «начнём с 1 октября на девять
  месяцев», «субподряд допускаем»;
- **ТЗ собирается по ходу разговора.** Объект, цель, документация, приёмка,
  особые условия записываются на каждом ходе, показываются строкой «Записал в
  заявку» и видны в панели заявки — не нужно ждать кнопки в конце.

Retrieval выполняется **после** решения модели и только детерминированным SQL.
LLM не решает, что искать, не ходит в базу и не может выдумать идентификатор: она
получает готовый отранжированный список и пишет по нему текст. Порядок карточек
задаёт SQL, а не модель. Выбор словами приходит номером в последнем показанном
списке, сроки — датами, которые разбирает код, условия — по белому списку из трёх
флагов. `ENABLE_ROUTER=false` (имя оставлено ради совместимости с существующими
`.env`) переводит ход на детерминированную ветку: без выбранной услуги любой
текст — поиск, с выбранной — ответ собирается из состояния заявки.

Деградация вместо отказа: недоступен эмбеддинг-сервис — поиск идёт по полнотекстовому
каналу; недоступна LLM — список приходит с шаблонным текстом; недоступен TZ Generator —
чат продолжает работать без панели готовности.

### Одна заявка на всех экранах

Диалог, форма конструктора и сформированный документ — три представления одной
заявки. Документ лежит в общем сторе (`frontend/src/workspace.ts`), поэтому одна
и та же карточка с версией, готовностью и ссылками на `.docx`/`.pdf` видна и в
конструкторе, и в панели чата, и в «Мои заявки» — и переживает переключение
вкладок и перезагрузку страницы. Готовое ТЗ отмечается в самом диалоге
(`tz_created`), так что ассистент знает о нём и не предлагает собрать заново.
«Начать заново» сбрасывает всё сразу: диалог, форму и документ.

### Состояние диалога

Живёт в `chat.session.state` (jsonb), а не в памяти сервиса и не в контексте модели.
Chat Service stateless: переживает рестарт в середине диалога, масштабируется
горизонтально. Смена слота каскадно сбрасывает зависимые — правило описано один раз
в `ChatState.ResetFrom`.

### Два транспорта для одного хода

SSE: один ход = один `POST`, ответ идёт потоком кадров (`meta`, `delta`, `block`,
`state`, `done`). WebSocket: один сокет на сессию, клиент шлёт кадр запроса на
каждый ход, сервер отвечает теми же именованными кадрами — без открытия нового
HTTP-соединения на каждый ход. Оба сводятся к одной и той же функции обработки
хода, различается только sink, в который пишутся события. Сервер по-прежнему
ничего не инициирует вне хода пользователя. Обрыв соединения не теряет ход:
события пишутся в `chat.turn.events`, клиент добирает их через
`GET /turns/{turnId}/stream?fromSeq=N` (для SSE) либо переподключением к `/ws`.
Повтор с тем же `Idempotency-Key` не выполняет ход второй раз, а отдаёт
сохранённые события; параллельный ход в одной сессии получает `409`.

## Как считается релевантность

`search.find_products` — один SQL-запрос, четыре канала:

| Канал | Вес | Зачем |
|---|---|---|
| Векторная близость (pgvector, HNSW) | 0.75 | синонимы, разговорные формулировки |
| Полнотекст по названию и категории | 0.04 | точные термины |
| Полнотекст по составу работ (этапы, операции) | 0.07 | слова, которых нет в названии услуги |
| Пословные триграммы | 0.03 | опечатки |
| Популярность по истории заказов | 0.03 | при прочих равных — то, что заказывают чаще |

Плюс бонусы: совпадение всех слов запроса `+0.04`, точное совпадение названия `+1.0`
(последнее — вне весов: это не «похоже по словам», а прямое указание услуги по имени).

Порядок определяет смысл, а не словарь. Заказчик описывает работы своими словами,
и услуга, у которой просто чаще встречается слово из запроса, регулярно
обгоняла ту, о которой действительно спрашивали. Поэтому лексические каналы
понижены до уточнения порядка внутри смыслово близких услуг: они по-прежнему
дают `matched_terms` и обоснования в карточках, но исхода не решают.

**Без эмбеддингов веса другие.** Когда модель эмбеддингов недоступна,
`TurnPipeline.EmbedAsync` отдаёт `NULL`, и функция возвращается к прежнему
лексическому набору (0.20 / 0.25 / 0.10 / 0.05, бонус за фразу 0.15): понижать
лексику там, где она единственный работающий канал, нечем — иначе вся выдача
провалилась бы ниже порогов уверенности и агент отвечал бы «не нашёл».

Три вещи, без которых гибрид врал на реальных данных:

* **Штраф за неинформативные чанки.** В выгрузке десятки услуг делят дословно одинаковый
  текст операций. Такой чанк одинаково «близок» к любому запросу, поэтому группа
  дубликатов стабильно занимала всю выдачу. Вклад канала делится на `1 + ln(df)`,
  где `df` — сколько услуг содержит этот же текст.
* **Отбор информативных слов запроса (IDF).** Встроенный русский словарь стоп-слов
  снимает не всё: «который» доживает до лексемы `котор` и совпадает с половиной
  каталога. Лексемы, встречающиеся более чем в 30% услуг, в поиске не участвуют
  и в доказательства не попадают.
* **Пословные триграммы вместо запроса целиком.** Прежнее `p.name %> запрос` на
  разговорной фразе не срабатывало никогда. Предел канала честный: перестановка
  соседних букв («скважину» → «скажвину») рушит три триграммы подряд и сюда не
  ловится — такой запрос вытягивает семантика либо уточняющий вопрос.

Функция возвращает `matched_terms` — слова запроса, которые реально совпали.
Из них, а не из порогов, строятся обоснования в карточках: если совпавших слов
нет, так и написано.

Ключевая деталь реализации: ANN вынесен в отдельный CTE с чистым `ORDER BY ... LIMIT` —
иначе планировщик не возьмёт HNSW-индекс и запрос выродится в полный перебор.

## Когда агент говорит «не нашёл»

`score` — сумма разнородных величин, поэтому абсолютный порог по нему бессмысленен:
шум на реальных данных набирал 0.34 при отсечке 0.15 и подавался как уверенная
находка. Решение принимает `TurnPipeline.Assess` по трём сигналам сразу:

| Сигнал | Порог | Переменная |
|---|---|---|
| Абсолютный уровень лидера | 0.20 / 0.45 | `SEARCH_MIN_SCORE`, `SEARCH_CONFIDENT_SCORE` |
| Отрыв от второго места | 0.005 | `SEARCH_MIN_MARGIN` |
| Близость, когда совпавших слов нет | 0.60 | `SEARCH_SEMANTIC_FLOOR` |

Отрыв от второго места почти не проверяется: после переноса веса на вектор
`score` на три четверти состоит из косинусной близости, а она у нескольких
профильных услуг закономерно похожа. Прежние 0.08 стали недостижимы, и
уверенная выдача уходила в «догадку» даже когда наверху стояла ровно та услуга,
о которой спрашивали. Шум держат два оставшихся сигнала; здесь осталась защита
от действительно плоской выдачи — совпадения балл в балл у услуг-дубликатов.

Три исхода: **уверенно** — обычная выдача; **похоже** — карточки помечены как догадка
(пунктирная рамка и тихая пометка «ближайшие по смыслу варианты» — сам текст
ответа уже говорит, что точного соответствия нет), рядом уточняющий вопрос;
**не нашёл** — карточек нет вовсе, только уточняющий вопрос.
В `analytics.search_log` поле `recognized` теперь означает «агент понял запрос», а не
«SQL что-то вернул» — иначе витрина нераспознанных запросов пустая при любом качестве.

## Поиск исполнителей до выбора услуги

`search.find_companies` отвечает на вопрос «кто вообще может это сделать» — по профилю
компании и по истории выполненных работ. Раньше такой вопрос пути не имел: `ops.find_executors`
требует `product_id` и даты, поэтому пользователю приходилось сначала угадать услугу.
Занятость здесь не показывается сознательно: без периода она не определена.

## Как ранжируются исполнители

`ops.find_executors`. Наблюдение по данным: этапы работ у компаний идут внахлёст и
покрывают почти весь год, поэтому бинарное «свободен / занят» бессмысленно — свободных
не будет ни одного. Загрузка считается **относительной**: число параллельных работ
компании в заданном периоде против самого загруженного кандидата.

```
score = (0.35·опыт_по_услуге + 0.30·(1−загрузка) + 0.25·рейтинг + 0.10·есть_история)
        × (0.85 если субподряд)
```

Кандидаты — компании с опытом по этой услуге или действующим договором; субподряд —
компании с опытом в той же категории работ. Каждый исполнитель приходит с массивом
`reasons`: сколько работ выполнено, когда завершена последняя, сколько работ ведёт
в этот период, какая загрузка, какой рейтинг.

## Как считается готовность ТЗ

Веса полей лежат в `tz.template.required_fields` и в сумме дают 100. Готовность —
сумма весов заполненных полей. Правила рисков лежат в `tz.template.risk_rules`
в виде маленького декларативного DSL:

```json
{"code":"model3d_no_source","severity":"warning",
 "title":"Выбрана 3D-модель без этапа подготовки исходных данных",
 "when":{"op":"and","args":[{"op":"flag","arg":"model3d"},
                            {"op":"missing_stage","arg":"исходн"}]}}
```

Операции DSL: `empty`, `empty_list`, `flag`, `missing_stage`, `duration_below_typical`,
`stages_without_docs`, `and` / `or` / `not`. Добавить новый риск — это `UPDATE` строки
в БД, а не релиз сервиса. Критичный риск блокирует выгрузку документа; проверка
дублируется на сервере, фронт лишь подсвечивает.

Структура разделов ТЗ взята из реальных шаблонов датасета (`Выгрузка из системы/Шаблоны ТЗ`):
все 16 документов сводятся к одному каноническому набору из 11 разделов.

## Аналитика MVP

Обе группы требований закрываются одним запросом `/api/v1/analytics/overview`:

* самые востребованные услуги по поисковым запросам;
* запросы, не распознанные агентом (лог `analytics.search_log`);
* наиболее часто сочетаемые услуги (совместная встречаемость в договорах);
* исполнители с наибольшим числом аналогичных работ;
* количество созданных ТЗ и средняя готовность;
* типичные ошибки и нарушения при формировании ТЗ (агрегация рисков);
* наиболее часто добавляемые этапы;
* перечень работ, пригодных для упаковки в типовой продукт.

## Ограничения прототипа

* Аутентификации нет. Ролей две — заказчик (НТЦ) и подрядчик (любая компания из
  каталога), переключаются селектором в шапке. Это демо-контекст: логина и пароля
  нет, роль хранится в браузере и уходит на сервер заголовком `X-Prostor-Actor`,
  который принимается на веру. Проверка «подрядчик отвечает только за свою
  компанию» в API нужна для согласованности интерфейса, а не как защита.
* Занятость исполнителей выводится из дат этапов исторических расчётов —
  отдельного календаря загрузки в выгрузке нет.
* Расценки загружены (`catalog.price`), но расчёт стоимости в MVP не реализован —
  это следующая итерация, данные для неё уже в схеме.
* Версионирование ТЗ реализовано: новый документ можно создать как новую версию
  существующего (`parentTzId`) или сохранить черновиком без финализации
  (`asDraft`), история версий — `GET /api/v1/tz/documents/{id}/versions` и вкладка
  «Мои заявки» в интерфейсе.
* Файл в MinIO не обязателен: если хранилище недоступно, документ фиксируется в БД
  и пересобирается из `payload` при скачивании.
