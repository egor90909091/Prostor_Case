# ПРОСТОР MVP — ИИ-агент умного поиска + умный конструктор ТЗ

Проект ИИ умного поиска платформы ПРОСТОР — одно приложение с общей навигацией:

* **ИИ-агент умного поиска.** Запрос на естественном языке → релевантные услуги с
  обоснованием → аналогичные выполненные работы → исполнители с обоснованием →
  связанные услуги → черновик заявки.
* **Умный конструктор ТЗ.** Сборка документа из типовых блоков, автоматическая
  структура по типу ТЗ, процент готовности, риски и рекомендации, выгрузка
  `.docx` и `.pdf`.
* **Единый поток.** Кнопка «Сформировать ТЗ» переносит услугу, этапы, сроки,
  исполнителей и условия из диалога в конструктор — заполнять заново ничего не нужно.

Всё построено на реальной выгрузке из ПРОСТОР: 51 услуга, 13 компаний, 20 договоров,
462 расчёта, 1676 этапов работ, 318 операций, 673 расценки.

Архитектурные решения и то, чего в проекте сознательно нет, — в
[`docs/architecture.md`](docs/architecture.md).

## Быстрый старт

```bash
docker compose up --build          # ~3 минуты на первую сборку
```

| Что | Адрес |
|---|---|
| Приложение | http://localhost:3000 |
| Chat Service (агент, каталог, аналитика) | http://localhost:8080 |
| TZ Generator (шаблоны, черновики, документы) | http://localhost:8081 |
| MinIO console | http://localhost:9001 (`minioadmin` / `minioadmin`) |
| PostgreSQL | `localhost:5432`, `prostor` / `prostor` |

Креды БД и MinIO — дефолты для локального прототипа, заданы в `docker-compose.yml`
через подстановки `${VAR:-дефолт}` и переопределяются через `.env` (см.
`.env.example`). В самом compose-файле ничего не захардкожено.

### Инициализация БД и «миграции»

База поднимается скриптами `db/init/*.sql` (схема → шаблоны ТЗ → seed → функции
поиска → согласование → демо-ТЗ). Официальный образ Postgres выполняет их по
алфавиту через `docker-entrypoint-initdb.d` — **но только когда `pgdata` volume
пустой**.

> **Ручные SQL-скрипты `db/init/` — это осознанное упрощение для прототипа, а не
> система миграций.** Здесь нет версионирования схемы, отката и накатывания на
> живую базу по одному шагу. В боевой реализации место `db/init/` займёт
> полноценный инструмент миграций (EF Core Migrations / Flyway / Liquibase) с
> историей версий и совместимостью вперёд/назад. Пока же:
> - изменили `db/init/` — пересоздайте volume:
>   `docker compose down -v && docker compose up --build`;
> - исключения — `04_functions.sql` и `06`–`09`: они идемпотентны
>   (`CREATE OR REPLACE`, `IF NOT EXISTS`) и накатываются на живую базу
>   (команда — в шапке каждого файла).

> **Доступ к данным — сырой SQL (Npgsql), без ORM.** Для прототипа так проще:
> схема маленькая и стабильная, а ядро — гибридный поиск и ранжирование
> (`search.find_products`, `ops.find_executors`) — всё равно выражается только
> на SQL. В боевой реализации CRUD-слой и миграции можно перевести на EF Core,
> оставив функции поиска сырым SQL (`FromSqlRaw` или функции БД).

Эмбеддинги каталога считает фоновый индексатор внутри Chat Service — несколько
секунд после старта. **Смена модели эмбеддингов требует переиндексации**
(индексатор трогает только строки с `embedding IS NULL`); покрытие видно в
`GET /health` (`index.ready`), сброс векторов — в
[`docs/architecture.md`](docs/architecture.md#3-схема-данных).

### Ключи моделей не обязательны

Без `LLM_API_KEY` чат отвечает шаблонным «стенографом»; без `EMBEDDING_BASE_URL`
каталог индексируется детерминированной заглушкой. Переключаются независимо,
сценарий проходит целиком без внешних вызовов. Единственное исключение —
экстракция полей ТЗ из диалога (кнопка «Генерация технического задания на
основании диалога»): она осмысленна только с реальной моделью. LLM и эмбеддинги —
разные OpenAI-совместимые endpoint'ы, настраиваются в `.env` (см. `.env.example`).

## Демо-сценарий за 90 секунд

1. http://localhost:3000, вкладка **ИИ-агент поиска**.
2. «Нужно оценить запасы по объекту» — придёт текст от агента и карточки услуг с
   рангом, релевантностью и обоснованием подбора.
3. Выбрать услугу — появятся датапикер с типовым сроком, аналогичные выполненные
   работы, связанные услуги и рекомендации по заявке.
4. Указать период — список исполнителей с рангом, опытом по услуге, загрузкой в
   периоде и объяснением выбора.
5. Выбрать исполнителей → отметить этапы работ → в чате появится готовность ТЗ с
   рисками.
6. **«Генерация технического задания на основании диалога»** — агент разберёт
   переписку и предложит значения текстовых полей ТЗ; каждое принимается
   отдельно. Только при заданном `LLM_API_KEY`.
7. **«Сформировать ТЗ в конструкторе»** — откроется конструктор с предзаполненными полями.
8. В конструкторе: включить «Построение 3D геологической модели» → появится риск
   «3D-модель без этапа подготовки исходных данных». Стереть объект работ →
   готовность упадёт, выгрузка заблокируется.
9. Заполнить недостающее → **«Сформировать документ»** → зона готового документа:
   предпросмотр, скачивание `.docx`/`.pdf`, переход в «Мои заявки».
10. Переключить роль справа сверху с **НТЦ** на подрядчика → **Входящие ТЗ**.
    Открыть направленное ТЗ, повесить замечание на раздел, **«На доработку»** с
    причиной.
11. Вернуть роль **НТЦ** → «Мои заявки»: категории «Черновики», «Готовы к
    отправке», «На согласовании», «Вернули с замечаниями», «Согласованы» со
    счётчиками. В «Вернули с замечаниями» — замечания подрядчика и кнопка
    **«Исправить раздел»**, открывающая конструктор на нужных полях. После правок —
    новая версия и повторное направление.
12. Вкладка **Аналитика** — витрины по поиску и по конструктору ТЗ плюс согласование.

## Архитектура

```
React (nginx)
  │  POST /turns (SSE) или один WebSocket на сессию — оба ведут в один обработчик хода
  ▼
Chat Service (C#)          ──синхронный HTTP──▶   TZ Generator (C#)
  slot filling, поиск, ранжирование                готовность, риски, docx/pdf
  │            │                                    │            │
  ▼            ▼                                    ▼            ▼
PostgreSQL  pgvector                            PostgreSQL     MinIO S3
```

Ни брокера, ни outbox, ни Redis. Сервер ничего не инициирует вне хода
пользователя; WebSocket — просто один канал на сессию вместо нового HTTP на
каждый ход. Оба транспорта вызывают одно тело обработчика и защищены
`Idempotency-Key`. Обоснования — в [`docs/architecture.md`](docs/architecture.md).

### Один ход диалога

| Вход | Эмбеддинг | SQL | LLM |
|---|---|---|---|
| Свободный текст | 0–1 (только если решено искать) | 0–2 запроса | 1 (разговор) или 2 (поиск) |
| Клик по карточке | 0 | 1 запрос | 0 |

Свободный текст обрабатывает один структурированный вызов модели — «мозг диалога»
([`Brain.cs`](backend/src/Prostor.Chat/Brain.cs)): за round-trip возвращает ответ
пользователю, намерение хода, данные для ТЗ, уместную карточку и подсказки.
Retrieval выполняется **после** решения модели и только детерминированным SQL —
LLM не решает, что искать, не ходит в базу и не может выдумать идентификатор.
Выбор словами приходит номером в последнем показанном списке, сроки — датами,
условия — по белому списку флагов. Подробности — в
[`docs/architecture.md`](docs/architecture.md#21-ход-диалога).

Деградация вместо отказа: нет эмбеддингов — поиск по полнотексту; нет LLM — список
с шаблонным текстом; нет TZ Generator — чат без панели готовности.

### Одна заявка на всех экранах

Диалог, форма конструктора и документ — три представления одной заявки. Документ
лежит в общем сторе ([`frontend/src/workspace.ts`](frontend/src/workspace.ts)),
поэтому карточка с версией, готовностью и ссылками на файлы одинаково видна в
конструкторе, в панели чата и в «Мои заявки», переживает переключение вкладок и
перезагрузку. «Начать заново» сбрасывает всё сразу.

### Состояние диалога

Живёт в `chat.session.state` (jsonb), не в памяти сервиса и не в контексте
модели. Chat Service stateless: переживает рестарт, масштабируется горизонтально.

## Как считается релевантность

`search.find_products` — один SQL-запрос, четыре канала (веса при активных
эмбеддингах):

| Канал | Вес | Зачем |
|---|---|---|
| Векторная близость (pgvector, HNSW) | 0.75 | синонимы, разговорные формулировки |
| Полнотекст по названию и категории | 0.04 | точные термины |
| Полнотекст по составу работ | 0.07 | слова, которых нет в названии услуги |
| Пословные триграммы | 0.03 | опечатки |
| Популярность по истории заказов | 0.03 | при прочих равных — то, что заказывают чаще |

Плюс бонусы: совпадение всех слов запроса `+0.04`, точное совпадение названия
`+1.0` (вне весов — прямое указание услуги по имени). Лексические каналы понижены
до уточнения порядка внутри смыслово близких услуг: они дают `matched_terms` и
обоснования в карточках, но исхода не решают. **Без эмбеддингов** функция
возвращается к чисто лексическому набору весов.

Три поправки, без которых гибрид врал на реальных данных: штраф за неинформативные
чанки (`1 + ln(df)` — десятки услуг делят дословный текст операций), отбор
информативных слов запроса по IDF (лексемы из >30% каталога не участвуют),
пословные триграммы вместо запроса целиком. Детали и пороги «уверенно / похоже /
не нашёл» (`TurnPipeline.Assess`) — в
[`docs/architecture.md`](docs/architecture.md).

### Как ранжируются исполнители

`ops.find_executors`. Этапы работ у компаний идут внахлёст почти весь год, поэтому
бинарное «свободен / занят» бессмысленно — загрузка считается **относительной**:
число параллельных работ в периоде против самого загруженного кандидата.

```
score = (0.35·опыт_по_услуге + 0.30·(1−загрузка) + 0.25·рейтинг + 0.10·есть_история)
        × (0.85 если субподряд)
```

`search.find_companies` отвечает на «кто вообще может это сделать» до выбора услуги
и периода — по профилю и истории работ (занятость там не определена).

### Как считается готовность ТЗ

Веса полей в `tz.template.required_fields` дают в сумме 100; готовность — сумма
весов заполненных полей. Правила рисков — декларативный DSL в
`tz.template.risk_rules` (`empty`, `flag`, `missing_stage`,
`duration_below_typical`, `stages_without_docs`, `and`/`or`/`not`). Новый риск —
это `UPDATE` строки, а не релиз. Критичный риск блокирует выгрузку (проверка
дублируется на сервере). Структура разделов — один канонический набор из 11
разделов, сведённый из 16 реальных шаблонов датасета.

### Chat Service — `:8080`

| Метод | Путь | Назначение |
|---|---|---|
| `POST` | `/api/v1/chat/sessions` | создать сессию |
| `POST` | `/api/v1/chat/sessions/{id}/turns` | ход диалога, ответ — поток SSE |
| `GET` | `/api/v1/chat/sessions/{id}/ws` | тот же ход по WebSocket (один сокет на сессию) |
| `GET` | `/api/v1/chat/sessions/{id}` \| `/state` | история и состояние / полное состояние для конструктора |
| `GET` | `/api/v1/chat/sessions/{id}/turns/{turnId}/stream?fromSeq=N` | дострим после обрыва (SSE) |
| `POST` | `/api/v1/catalog/products/search` | гибридный поиск услуг |
| `GET` | `/api/v1/catalog/products/{id}` \| `/stages` \| `/operations` \| `/related` \| `/similar` \| `/risks` | карточка и состав услуги |
| `POST` | `/api/v1/executors/discover` \| `/search` | подбор исполнителей без услуги/периода / с обоснованием |
| `POST` | `/api/v1/review/draft` | LLM-ревью черновика ТЗ |
| `GET` | `/api/v1/analytics/overview` | витрины аналитики |

### TZ Generator — `:8081`

| Метод | Путь | Назначение |
|---|---|---|
| `GET` | `/api/v1/tz/templates` | шаблоны и веса полей |
| `POST` | `/api/v1/tz/drafts` | черновик: готовность, риски, разделы (без побочных эффектов) |
| `POST` | `/api/v1/tz/documents` | сборка `.docx` в MinIO и БД; `parentTzId` — новая версия, `asDraft` — без финализации |
| `GET` | `/api/v1/tz/documents` \| `/{id}` \| `/{id}/file` | список / метаданные / файл (`?format=pdf` — на лету) |
| `GET` | `/api/v1/tz/documents/{id}/versions` | история версий (`parent_tz_id`) |
| `POST`/`GET` | `/api/v1/tz/documents/{id}/assignments` | направить ТЗ подрядчикам (`companyIds`, `note`) / статусы по цепочке |
| `GET` | `/api/v1/tz/inbox` | входящие ТЗ подрядчика (компания — из заголовка роли) |
| `POST` | `/api/v1/tz/assignments/{id}/view` \| `/decision` | «открыл ТЗ» / решение `approved`\|`revision`\|`rejected` |
| `GET`/`POST` | `/api/v1/tz/documents/{id}/comments` | тред замечаний; `sectionKey` привязывает к разделу |
| `POST` | `/internal/tz/draft` | тот же черновик для вызова из Chat Service |

Роль передаётся заголовком `X-Prostor-Actor: customer:ntc` либо
`contractor:{company_id}` — демо-контекст, не авторизация (см. ниже).

## Аналитика MVP

Один запрос `/api/v1/analytics/overview`: востребованные услуги по запросам, доля
распознанных запросов по дням, часто сочетаемые услуги, исполнители с числом
аналогичных работ, число созданных ТЗ и средняя готовность, типичные ошибки при
формировании ТЗ, часто добавляемые этапы, работы, пригодные для типового продукта.

## Ограничения прототипа

* **Инициализация БД — ручные SQL-скрипты `db/init/`, а не система миграций.**
  Осознанное упрощение; в боевой реализации — полноценный инструмент миграций
  (см. «Инициализация БД и „миграции“» выше).
* **Аутентификации нет.** Роли (заказчик НТЦ / подрядчик / администратор
  платформы) переключаются селектором в шапке. Роль хранится в браузере и уходит
  на сервер заголовком `X-Prostor-Actor`, который принимается на веру. Проверка
  «подрядчик отвечает только за свою компанию» нужна для согласованности
  интерфейса, а не как защита. Заказчик пока один — фильтрации показателей по
  заказчику ещё нет, разделены наборы панелей.
* **Занятость исполнителей** выводится из дат этапов исторических расчётов —
  отдельного календаря загрузки в выгрузке нет.
* **Расчёт стоимости не реализован.** Расценки загружены (`catalog.price`), данные
  для следующей итерации уже в схеме.
* **Файл в MinIO не обязателен:** если хранилище недоступно, документ фиксируется
  в БД и пересобирается из `payload` при скачивании.
