# Архитектура решения

Документ для архитектурного комитета: компоненты, потоки, схема данных,
обоснование выбора технологий и того, чего в решении сознательно нет.

## 1. Компоненты

| Компонент | Технология | Ответственность |
|---|---|---|
| Web | React 18 + TypeScript + Vite, отдаётся nginx | Единое приложение: чат-агент, конструктор ТЗ, аналитика. Общая навигация, общее состояние сессии |
| Chat Service | C# .NET 8, minimal API | Состояние диалога, поиск услуг, подбор исполнителей, стриминг ответа, логирование аналитики, фоновая индексация каталога |
| TZ Generator | C# .NET 8, minimal API | Шаблоны ТЗ, сборка черновика, расчёт готовности, проверка рисков, генерация `.docx`, работа с хранилищем |
| PostgreSQL 16 + pgvector | `pgvector/pgvector:pg16` | Каталог, история договоров и расчётов, сессии, ТЗ, эмбеддинги, витрины аналитики |
| MinIO | S3-совместимое хранилище | Тела документов `.docx` (PDF собирается на лету) |

Границы сервисов проведены по частоте изменений и по нагрузке: агент меняется
вместе с поисковой логикой и промптами, генератор ТЗ — вместе с шаблонами
документов и правилами согласования. Общая у них только база.

## 2. Потоки

### 2.1 Ход диалога

```
 React ──POST /turns (Accept: text/event-stream)──▶ Chat Service
                                                     │ SELECT state
                                         ┌───────────┴────────────┐
                         свободный текст │                        │ действие (клик)
                                         ▼                        ▼
                    контекст хода из БД                  редьюсер состояния
             (карточка услуги, этапы, похожие                   │
              работы, хвост диалога, слоты)          1× SQL следующего шага
                                         │                          │
                    1× LLM «мозг диалога» (JSON,             текст из шаблона
                    без стрима): reply + intent +                   │
                    facts + offer + suggestions                     │
                                         │                          │
                       ┌─────────────────┴───────────────┐          │
                       ▼                                 ▼          │
              запись фактов кодом                 intent=search_*   │
        (даты парсятся, флаги по белому            1× embed(text)   │
         списку, поля ТЗ — как есть)                     │          │
                       │                        1× SQL find_products│
                       ▼                          / find_companies  │
             reply -> дельты SSE                        │           │
                       │                        1× LLM (только текст)
                       ▼                                │           │
             карточка следующего шага (offer)           │           │
             через гейты кода: слоты + анти-повтор      │           │
                       └────────────────┬───────────────┘───────────┘
                                        ▼
                               SSE: meta → delta* → block* → state → done
                                                     │
                                         UPDATE state, INSERT message, turn.events
```

Ход свободного текста — это один структурированный вызов модели (`Brain.cs`,
`ILlm.CompleteJsonAsync` со схемой `dialogue_turn`) плюс детерминированный код
вокруг него. Модель за один round-trip отвечает сразу на четыре вопроса хода:

| поле        | что это                                                    |
|-------------|------------------------------------------------------------|
| `reply`     | что сказать человеку — всегда, в том числе при поиске       |
| `intent`    | `answer` / `search_services` / `search_executors` / `pick_option` / `restart` |
| `facts`     | данные для ТЗ, прозвучавшие в разговоре (включая сроки и условия) |
| `offer`     | какую карточку уместно показать следующей                  |
| `suggestions` | 2–4 короткие подсказки следующей реплики пользователя    |

Разделение ответственности прежнее и жёсткое: модель решает, ЧТО сказать и КУДА
направить ход, но не ЧТО искать в базе и какими идентификаторами оперировать —
их она не видит. Поисковым запросом остаётся текст пользователя (модель может
лишь до-собрать его из контекста в `query`, например подставить вид работ в «а
найди подешевле»). Выбор услуги словами («давай первый») приходит номером в
последнем показанном списке (`ChatState.LastOptions`), а не идентификатором.
Сроки, названные словами, разбираются `DateOnly.TryParse` и идут ровно тем же
путём, что и карточка периода (`ApplyPeriodAsync`), — поведение кнопок и
разговора не может разъехаться. Условия берутся по белому списку из трёх флагов.
Это по-прежнему не agentic tool-calling из раздела 5: у модели нет инструментов
с побочными эффектами, есть один JSON-ответ, который код валидирует и применяет.

Карточки — предложение поверх разговора, а не шаг мастера. Предложение модели
(`offer`) проходит гейты кода в `TurnPipeline.OfferAsync`: нельзя спрашивать
исполнителей раньше сроков (без периода занятость не определена — такой offer
подменяется на период), нельзя показывать список этапов до выбора услуги, и
нельзя показать одно и то же предложение два хода подряд (`ChatState.LastOffer`)
— иначе диалог превращается в назойливую анкету. Пользователь может
проигнорировать любую карточку и продолжить разговор словами: слоты заполняются
из разговора точно так же, как из кликов.

Сущности для ТЗ вытаскиваются на каждом ходе, а не одной кнопкой в конце.
Записанное показывается блоком `captured` («Записал в заявку: объект работ — …»)
и уезжает в снапшот состояния, поэтому боковая панель показывает собранное ТЗ по
мере разговора, и человек сразу видит, если его поняли неправильно. Кнопка
«Генерация ТЗ на основании диалога» (`extract_tz`) осталась как разбор всего
транскрипта разом — теперь это подстраховка, а не единственный путь.

Контекст хода собирается кодом из базы: карточка услуги, типовые этапы, похожие
выполненные работы, уже заполненные поля ТЗ, последний показанный список и хвост
транскрипта диалога, плюс сегодняшняя дата (без неё «с сентября» не превратить в
период). Именно отсутствие этого контекста раньше и порождало заготовленные
фразы: классификатор не знал деталей услуги, а консультация не умела предлагать
следующий шаг.

Деградация: отказ модели (недоступна, таймаут, битый JSON, отсутствие ключа)
не роняет ход — решение принимает детерминированный `Brain.Fallback`. Без
выбранной услуги любой свободный текст остаётся поиском, как раньше; с выбранной
услугой ответ собирается из фактического состояния заявки (услуга, сроки,
исполнители, этапы, чего не хватает), а не из одной заготовки. `ENABLE_ROUTER=false`
включает эту ветку принудительно, без пересборки образа. Имя переменной оставлено
прежним ради совместимости с существующими `.env`.

Бюджет вызовов на ход не вырос: разговор — один нестримящийся вызов (раньше было
два: роутер + консультация), поиск — тот же вызов плюс 1 embed + 1 SQL + 1
стримящийся вызов на формулировку выдачи. Действие (клик) — по-прежнему ноль
вызовов моделей.

### 2.2 Переход из Кейса 2 в Кейс 1

Кнопка «Сформировать ТЗ» передаёт в конструктор `sessionId`. Конструктор
запрашивает `GET /api/v1/chat/sessions/{id}/state` и получает то же состояние,
которым оперировал агент: услуга, шаблон, период, этапы, операции, исполнители,
условия работ. Пользователь не вводит ничего заново.

Одна заявка на весь фронт. Диалог, форма конструктора и сформированный документ
— три представления одного и того же, и живут они в трёх разных местах по
разным причинам:

| что | где хранится | почему |
|---|---|---|
| диалог | `chat.session` в Postgres, в браузере только указатель | история — данные сервиса, а не браузера |
| форма ТЗ | `localStorage` (`prostor.constructor.state`) | у конструктора нет серверной сессии; черновик не должен теряться при F5 |
| документ заявки | `localStorage` + внешний стор (`workspace.ts`) | нужен всем экранам сразу: зоне результата, панели чата, «Мои заявки» |

Документ раньше жил только в состоянии `ConstructorView`, а вкладки
рендерились условно — конструктор размонтировался при переходе в чат, и зона
готового документа исчезала вместе с ним; чат и «Мои заявки» о документе вообще
не знали. Теперь и чат, и конструктор смонтированы постоянно (скрываются через
`hidden`), а документ читается из общего стора через `useSyncExternalStore` —
одна и та же карточка и одни и те же ссылки на файлы во всех разделах, включая
соседнюю вкладку браузера (событие `storage`).

Постоянно смонтированный конструктор меняет и семантику предзаполнения: оно
происходит не «на монтировании», а по явному запросу — `chatRequest` (кнопка
«Сформировать ТЗ» в чате, срабатывает только на пустой форме) и `editRequest`
(«Открыть в конструкторе» в «Мои заявки», перечитывает документ всегда,
поэтому передаётся парой `{tzId, at}`). Иначе повторный заход на вкладку
затирал бы правки пользователя данными из БД.

Готовый (не черновиковый) документ чат отмечает у себя ходом `tz_created`: в
состоянии сессии появляется `tzId`, шаг переходит в `TzReady`, а в ленте —
блок `tz_ready` со ссылками на оба формата. Так ассистент знает, что ТЗ уже
сформировано, и не предлагает собрать его заново.

«Начать заново» в чате сбрасывает заявку целиком: сессию диалога, форму
конструктора, очередь непринятых подсказок и документ. Раньше кнопка обещала
это текстом («Сбросить чат и черновик ТЗ?»), но чистила только диалог.

Свободный текст полей ТЗ (цель, периметр, исходные данные, документация,
приёмка, объект, заказчик) в `chat.session.state` не попадает автоматически —
это отдельное явное действие `extract_tz` (кнопка «Генерация технического
задания на основании диалога»). Оно запускает один нестримящийся JSON-вызов
LLM: на вход — транскрипт всего диалога (`Db.GetDialogueTranscriptAsync`) и
список текстовых полей шаблона с подсказками (`TzClient.GetTextFieldsAsync` →
`GET /api/v1/tz/templates`), модель раскладывает переписку по этим полям.
Результат — блок `suggested_fields`; каждое поле пользователь принимает
отдельно обычным `set_field`, ничего не применяется молча. Разбор ответа
устойчив к мусору вокруг JSON и делает один повторный вызов при невалидном
ответе (`OpenAiLlm.CompleteJsonAsync`); при `LLM_STRUCTURED_OUTPUTS=true`
вдобавок уходит `response_format: json_schema` с откатом на `json_object`,
если провайдер схему не принял. Без `LLM_API_KEY` действие возвращает пустой
результат — экстракция работает только с реальной моделью.

### 2.3 Генерация документа

```
Конструктор ──POST /tz/drafts──▶ TZ Generator      (на каждое изменение, без побочных эффектов)
                                       │
                                 готовность %, риски, разделы
                                       │
Конструктор ──POST /tz/documents──▶ TZ Generator
                                       ├─ повторная валидация (422, если критичные риски)
                                       ├─ TzLayout: содержание документа (общая модель)
                                       ├─ сборка WordprocessingML
                                       ├─ PUT в MinIO
                                       └─ INSERT tz.document (метаданные + payload)

Скачивание ──GET /tz/documents/{id}/file[?format=pdf]──▶ TZ Generator
                                       ├─ .docx  — из MinIO, иначе пересборка из payload
                                       └─ .pdf   — всегда сборка из payload (в хранилище не лежит)
```

Выгрузка в двух форматах строится из одной модели документа (`TzLayout`):
список блоков (абзацы с выключкой, заголовки, разрыв страницы, подписи сторон)
собирается один раз, а `DocxWriter` и `PdfWriter` только по-разному его
выражают. Иначе второй формат означал бы второй экземпляр структуры ТЗ — с
гарантией со временем разойтись с первым.

В хранилище лежит только `.docx`: PDF — представление того же документа, а не
отдельная сущность. Поэтому он собирается на лету и доступен в том числе для
документов, созданных до появления формата, а версионировать и синхронизировать
два файла не требуется.

Чат вызывает тот же расчёт через `POST /internal/tz/draft` — синхронным HTTP
с таймаутом 5 секунд и одним ретраем. При недоступности генератора диалог
продолжается без панели готовности.

## 3. Схема данных

```
catalog.company ──┐
                  ├── ops.contract ── ops.contract_product ──┐
catalog.product ──┼── catalog.operation                      │
                  ├── catalog.price                          │
                  └── ops.calc ── ops.stage ──▶ ops.booking (materialized view)
                                                     │
              search.product_chunk (vector 1024 — bge-m3, HNSW + GIN по chunk_tsv)
              search.company_chunk
              search.embedding_cache

chat.session ── chat.message
             └─ chat.turn (events jsonb — для дострима после обрыва)

tz.template (sections, required_fields, risk_rules — всё в jsonb)
tz.document (payload, readiness, risks, storage_key, version, parent_tz_id, status)
          └─ tz.assignment (направление версии ТЗ компании: статус согласования)
          └─ tz.comment    (замечания и вердикты; тред по корню цепочки версий)

analytics.product_stats · product_cooccurrence · company_product_stats  (materialized views)
analytics.search_log · analytics.event                                   (сырые события)
```

Ключевые решения по данным:

* **Занятость — не таблица, а проекция.** `ops.booking` — materialized view над
  реальными этапами расчётов. Отдельная сущность «бронь» потребовала бы
  синхронизации с историей и разъехалась бы с ней на первой же правке.
* **Дубли продуктов схлопываются в ETL.** В выгрузке одна услуга встречается под
  разными `product_id` в разных файлах; каноническим выбирается тот, что
  фигурирует в расчётах, остальные переписываются во всех ссылках.
* **Правила ТЗ — данные, а не код.** Веса полей и правила рисков лежат в
  `tz.template` в jsonb и интерпретируются сервисом. Новый риск — `UPDATE`,
  а не релиз.
* **Дубликаты описаний штрафуются, а не чистятся.** Десятки услуг в выгрузке
  делят дословно одинаковый текст операций. Схлопывать их в ETL нельзя — это
  разные услуги с разной историей и разными исполнителями. Поэтому неинформативность
  учитывается на поиске: вклад канала делится на `1 + ln(df)`, где `df` — сколько
  услуг содержит тот же текст. Без этого группа дубликатов занимала всю выдачу.
* **Индекс эмбеддингов не самообновляемый.** Индексатор заполняет только
  `embedding IS NULL`, поэтому смена модели требует явного сброса векторов.
  Состояние покрытия отдаётся в `GET /health` (`index.ready`) — молчаливо
  несовместимый индекс страшнее упавшего сервиса, потому что выглядит рабочим.
* **Согласование — отдельная сущность, а не поле документа.** `tz.document.status`
  отвечает на вопрос «черновик или готовый документ», то есть про готовность.
  Согласование — про процесс, и оно своё у каждого подрядчика: одно ТЗ можно
  направить нескольким, и каждый отвечает независимо. Поэтому статус живёт в
  `tz.assignment` по паре (версия ТЗ, компания), а не в документе.
* **Тред замечаний привязан к корню цепочки версий.** `root_tz_id` — это
  `coalesce(parent_tz_id, tz_id)`. Правки по замечаниям создают новую версию
  документа; если бы обсуждение висело на `tz_id`, подрядчик после повторного
  направления видел бы пустой экран вместо истории разговора.
* **Замечание указывает на раздел ТЗ.** `tz.comment.section_key` — ключ из
  `tz.base_sections()`, того же набора, по которому собирается документ. Поэтому
  из замечания заказчик попадает прямо в поля этого раздела в конструкторе,
  а не ищет глазами, о каком месте документа речь.
* **Витрины — materialized views.** Каталог меняется десятками позиций в день,
  пересчёт занимает секунды, `REFRESH` вызывается вместе с загрузкой данных.

## 4. Обоснование технологий

| Выбор | Почему |
|---|---|
| PostgreSQL + pgvector в одной базе | Каталог маленький (сотни чанков) и меняется редко. Отдельный векторный движок дал бы плюс инстанс и постоянную синхронизацию с каталогом ради задачи, которую расширение решает одним индексом |
| HNSW, а не IVFFlat | Не требует обучения на данных и не деградирует, когда каталог дополняется. На таком объёме разница в построении индекса незаметна |
| Гибридный поиск | Чистый вектор проваливается на кодах и терминах, чистый полнотекст — на разговорных формулировках. Отдельный канал по составу работ ловит слова, которых нет в названии услуги |
| Долгий HTTP со стримом SSE как основной транспорт, WebSocket — опциональный | Серверу нечего инициировать вне хода пользователя ни в том, ни в другом случае: WebSocket здесь не про server push, а про один канал на сессию вместо нового HTTP-соединения на каждый ход. Оба транспорта ведут в один и тот же обработчик хода (`/turns` и `/ws`) |
| Синхронный HTTP между сервисами | Генерация документа занимает десятки миллисекунд, пользователь ждёт результат. Брокер здесь добавил бы очередь, поллинг статуса и обработку дублей |
| `.docx` без внешней библиотеки | `docx` — это zip с тремя обязательными частями. Меньше зависимостей в образе и полный контроль над разметкой шаблона |
| `.pdf` без внешней библиотеки | Тот же расчёт: PDF — это дерево объектов и поток команд рисования. Дороже, чем docx (нужен разбор TrueType и встраивание шрифта), но альтернативой был либо NuGet-пакет со своей моделью документа, либо LibreOffice в образе ради конвертации |
| Шрифт из пакета образа, а не из репозитория | Кириллицы нет ни в одном из «стандартных 14» шрифтов PDF, поэтому файл шрифта обязателен. `fonts-dejavu-core` — 2 МБ в образе против 750 КБ бинарника в git; путь переопределяется через `PDF_FONT_REGULAR` |
| Заглушки моделей по умолчанию | Прототип должен разворачиваться и демонстрироваться без ключей и без внешней сети |

## 5. Чего в решении нет и почему

| Компонент | Почему не нужен |
|---|---|
| RabbitMQ / Kafka | Нет фоновых задач, которых пользователь не ждёт прямо сейчас |
| Transactional outbox | Outbox решает проблему «сообщение отправлено, транзакция откатилась». Нет брокера — нет проблемы |
| Redis | Состояние сессии всё равно должно переживать рестарт, то есть писаться в Postgres. Второе хранилище дало бы рассинхрон |
| Агентные фреймворки, произвольный tool-calling | Сценарий линейный и известен заранее. Дать модели самой формировать и выполнять запросы к базе — это недетерминированный порядок и риск выдуманных идентификаторов. Единственное исключение — два инструмента из §2.1 (`search_services`, `search_executors`): оба без аргументов и без побочных эффектов, решают только «когда» и «в какую из двух» передать ход уже существующему детерминированному SQL-поиску, не «что» и не «как» искать |
| Оценка релевантности моделью (LLM-as-judge) | Решение «уверенно / похоже / не нашёл» принимает `TurnPipeline.Assess` по измеримым признакам: уровень балла, отрыв от второго места, наличие совпавших слов. Это воспроизводимо, объяснимо пользователю и не стоит лишнего вызова модели |
| Отдельный сервис индексации | Каталог меняется десятками позиций в день. Индексатор живёт фоновой задачей в Chat Service |
| Аутентификация и разграничение доступа | Ролей в системе две — заказчик (НТЦ) и подрядчик (компания из `catalog.company`), и переключаются они селектором в шапке. Это демо-контекст, а не учётные записи: логина и пароля нет, роль лежит в `localStorage` и уходит на бэкенд заголовком `X-Prostor-Actor`, который принимается на веру (см. `Prostor.Tz/Actor.cs`, `frontend/src/identity.ts`). Настоящая авторизация в прототипе была бы формой без содержания: подделать заголовок тривиально, а показывать замок, за которым ничего нет, хуже, чем честно назвать это переключателем демо-роли. Проверка «подрядчик отвечает только за свою компанию» в API оставлена ради согласованности интерфейса, а не как защита |

Задел на будущее делается дёшево: если появится пакетная генерация ТЗ или отправка
на согласование по почте, добавляется таблица `job` со статусом и воркер в том же
процессе. Брокер имеет смысл, когда воркеров станет больше одного и они разъедутся
по разным сервисам.

## 6. Отказоустойчивость

| Отказ | Поведение |
|---|---|
| Эмбеддинг-сервис недоступен | Поиск деградирует до полнотекстового канала, пользователю сообщается о снижении точности |
| LLM недоступна | Список услуг приходит с шаблонным текстом, сценарий не прерывается |
| TZ Generator недоступен | Диалог продолжается без панели готовности |
| MinIO недоступен | Документ фиксируется в БД, файл пересобирается из `payload` при скачивании |
| Обрыв соединения в середине хода | Ход дописывается в БД независимо от соединения, клиент добирает события по `seq` |
| Повторная отправка | `Idempotency-Key` возвращает результат первого хода |
| Параллельный ход в одной сессии | `409 Conflict` с идентификатором активного хода |
