# Архитектура решения

Документ для архитектурного комитета: компоненты, потоки, схема данных,
обоснование выбора технологий и того, чего в решении сознательно нет.

## 1. Компоненты

| Компонент | Технология | Ответственность |
|---|---|---|
| Web | React 18 + TypeScript + Vite, отдаётся nginx | Единое приложение: чат-агент, конструктор ТЗ, аналитика. Общая навигация, общее состояние сессии |
| Chat Service | C# .NET 8, minimal API | Состояние диалога, поиск услуг, подбор исполнителей, стриминг ответа, логирование аналитики, фоновая индексация каталога |
| TZ Generator | C# .NET 8, minimal API | Шаблоны ТЗ, сборка черновика, расчёт готовности, проверка рисков, генерация `.docx`, работа с хранилищем |
| PostgreSQL 16 + pgvector | `pgvector/pgvector:pg16` | Каталог, история договоров и расчётов, сессии, ТЗ, эмбеддинги, витрины аналитики |
| MinIO | S3-совместимое хранилище | Тела документов `.docx` |

Границы сервисов проведены по частоте изменений и по нагрузке: агент меняется
вместе с поисковой логикой и промптами, генератор ТЗ — вместе с шаблонами
документов и правилами согласования. Общая у них только база.

## 2. Потоки

### 2.1 Ход диалога

```
React ──POST /turns (Accept: text/event-stream)──▶ Chat Service
                                                    │ SELECT state
                                        ┌───────────┴────────────┐
                        свободный текст │                        │ действие (клик)
                                        ▼                        ▼
                        1× LLM-роутер (без стрима,          редьюсер состояния
                        tool_choice=auto, единственный              │
                        инструмент search_services)         1× SQL следующего шага
                                        │                            │
                        ┌───────────────┴────────────┐       текст из шаблона
              инструмент│                             │текст         │
              вызван    ▼                             ▼              │
                1× embed(text)                консультация:          │
                        │                    ответ из decision,       │
                1× SQL find_products         SQL не выполняется       │
                        │                             │               │
                1× LLM (только текст)                 │               │
                        └───────────────┬──────────────────────────┘
                                                    ▼
                              SSE: meta → delta* → block* → state → done
                                                    │
                                        UPDATE state, INSERT message, turn.events
```

Retrieval по-прежнему выполняется только детерминированным SQL и только после
того, как решение принято: модель не строит запрос сама, не ходит в базу и не
может выдумать идентификатор — у `search_services` нет аргументов, поисковым
запросом для `find_products` остаётся исходный текст пользователя, а не то, что
могла бы пересказать модель. Единственное, что теперь решает модель на свободном
тексте, — вызывать ли этот путь на конкретном ходу, или ответить пользователю
текстом без обращения к БД (свободная консультация). Это узкий, single-purpose
tool call с фиксированной детерминированной реализацией на один HTTP round-trip
(`ILlm.DecideAsync`, без стрима — сознательно не смешиваем streaming и tool
calling, чтобы не зависеть от того, как конкретный OpenAI-совместимый провайдер
держит их комбинацию), а не agentic tool-calling, от которого отказались в
разделе 5: там речь про произвольные инструменты с произвольными аргументами
и побочными эффектами. Здесь инструмент один, без параметров, без побочных
эффектов, и переключает он только то, какая из двух уже существующих
детерминированных веток хода выполнится дальше.

На свободный текст теперь до двух вызовов LLM вместо одного: нестримящийся
роутер (короткий ответ, доли секунды) и, если решено консультировать или решено
искать, — стримящийся текстовый ответ, как и раньше. Ход перестаёт укладываться
в фиксированный «1 LLM-вызов» из таблицы в README, но остаётся ограниченным
сверху двумя вызовами. Переменная `ENABLE_ROUTER=false` полностью отключает
роутер и возвращает прежнее поведение («любой свободный текст — это поиск») без
пересборки образа — на случай, если провайдер плохо держит tool calling.

### 2.2 Переход из Кейса 2 в Кейс 1

Кнопка «Сформировать ТЗ» передаёт в конструктор `sessionId`. Конструктор
запрашивает `GET /api/v1/chat/sessions/{id}/state` и получает то же состояние,
которым оперировал агент: услуга, шаблон, период, этапы, операции, исполнители,
условия работ. Пользователь не вводит ничего заново.

### 2.3 Генерация документа

```
Конструктор ──POST /tz/drafts──▶ TZ Generator      (на каждое изменение, без побочных эффектов)
                                       │
                                 готовность %, риски, разделы
                                       │
Конструктор ──POST /tz/documents──▶ TZ Generator
                                       ├─ повторная валидация (422, если критичные риски)
                                       ├─ сборка WordprocessingML
                                       ├─ PUT в MinIO
                                       └─ INSERT tz.document (метаданные + payload)
```

Чат вызывает тот же расчёт через `POST /internal/tz/draft` — синхронным HTTP
с таймаутом 5 секунд и одним ретраем. При недоступности генератора диалог
продолжается без панели готовности.

## 3. Схема данных

```
catalog.company ──┐
                  ├── ops.contract ── ops.contract_product ──┐
catalog.product ──┼── catalog.operation                      │
                  ├── catalog.price                          │
                  └── ops.calc ── ops.stage ──▶ ops.booking (materialized view)
                                                     │
              search.product_chunk (vector 1024 — bge-m3, HNSW + GIN по chunk_tsv)
              search.company_chunk
              search.embedding_cache

chat.session ── chat.message
             └─ chat.turn (events jsonb — для дострима после обрыва)

tz.template (sections, required_fields, risk_rules — всё в jsonb)
tz.document (payload, readiness, risks, storage_key, version)

analytics.product_stats · product_cooccurrence · company_product_stats  (materialized views)
analytics.search_log · analytics.event                                   (сырые события)
```

Ключевые решения по данным:

* **Занятость — не таблица, а проекция.** `ops.booking` — materialized view над
  реальными этапами расчётов. Отдельная сущность «бронь» потребовала бы
  синхронизации с историей и разъехалась бы с ней на первой же правке.
* **Дубли продуктов схлопываются в ETL.** В выгрузке одна услуга встречается под
  разными `product_id` в разных файлах; каноническим выбирается тот, что
  фигурирует в расчётах, остальные переписываются во всех ссылках.
* **Правила ТЗ — данные, а не код.** Веса полей и правила рисков лежат в
  `tz.template` в jsonb и интерпретируются сервисом. Новый риск — `UPDATE`,
  а не релиз.
* **Дубликаты описаний штрафуются, а не чистятся.** Десятки услуг в выгрузке
  делят дословно одинаковый текст операций. Схлопывать их в ETL нельзя — это
  разные услуги с разной историей и разными исполнителями. Поэтому неинформативность
  учитывается на поиске: вклад канала делится на `1 + ln(df)`, где `df` — сколько
  услуг содержит тот же текст. Без этого группа дубликатов занимала всю выдачу.
* **Индекс эмбеддингов не самообновляемый.** Индексатор заполняет только
  `embedding IS NULL`, поэтому смена модели требует явного сброса векторов.
  Состояние покрытия отдаётся в `GET /health` (`index.ready`) — молчаливо
  несовместимый индекс страшнее упавшего сервиса, потому что выглядит рабочим.
* **Витрины — materialized views.** Каталог меняется десятками позиций в день,
  пересчёт занимает секунды, `REFRESH` вызывается вместе с загрузкой данных.

## 4. Обоснование технологий

| Выбор | Почему |
|---|---|
| PostgreSQL + pgvector в одной базе | Каталог маленький (сотни чанков) и меняется редко. Отдельный векторный движок дал бы плюс инстанс и постоянную синхронизацию с каталогом ради задачи, которую расширение решает одним индексом |
| HNSW, а не IVFFlat | Не требует обучения на данных и не деградирует, когда каталог дополняется. На таком объёме разница в построении индекса незаметна |
| Гибридный поиск | Чистый вектор проваливается на кодах и терминах, чистый полнотекст — на разговорных формулировках. Отдельный канал по составу работ ловит слова, которых нет в названии услуги |
| Долгий HTTP со стримом SSE как основной транспорт, WebSocket — опциональный | Серверу нечего инициировать вне хода пользователя ни в том, ни в другом случае: WebSocket здесь не про server push, а про один канал на сессию вместо нового HTTP-соединения на каждый ход. Оба транспорта ведут в один и тот же обработчик хода (`/turns` и `/ws`) |
| Синхронный HTTP между сервисами | Генерация документа занимает десятки миллисекунд, пользователь ждёт результат. Брокер здесь добавил бы очередь, поллинг статуса и обработку дублей |
| `.docx` без внешней библиотеки | `docx` — это zip с тремя обязательными частями. Меньше зависимостей в образе и полный контроль над разметкой шаблона |
| Заглушки моделей по умолчанию | Прототип должен разворачиваться и демонстрироваться без ключей и без внешней сети |

## 5. Чего в решении нет и почему

| Компонент | Почему не нужен |
|---|---|
| RabbitMQ / Kafka | Нет фоновых задач, которых пользователь не ждёт прямо сейчас |
| Transactional outbox | Outbox решает проблему «сообщение отправлено, транзакция откатилась». Нет брокера — нет проблемы |
| Redis | Состояние сессии всё равно должно переживать рестарт, то есть писаться в Postgres. Второе хранилище дало бы рассинхрон |
| Агентные фреймворки, произвольный tool-calling | Сценарий линейный и известен заранее. Дать модели самой формировать и выполнять запросы к базе — это недетерминированный порядок и риск выдуманных идентификаторов. Единственное исключение — два инструмента из §2.1 (`search_services`, `search_executors`): оба без аргументов и без побочных эффектов, решают только «когда» и «в какую из двух» передать ход уже существующему детерминированному SQL-поиску, не «что» и не «как» искать |
| Оценка релевантности моделью (LLM-as-judge) | Решение «уверенно / похоже / не нашёл» принимает `TurnPipeline.Assess` по измеримым признакам: уровень балла, отрыв от второго места, наличие совпавших слов. Это воспроизводимо, объяснимо пользователю и не стоит лишнего вызова модели |
| Отдельный сервис индексации | Каталог меняется десятками позиций в день. Индексатор живёт фоновой задачей в Chat Service |

Задел на будущее делается дёшево: если появится пакетная генерация ТЗ или отправка
на согласование по почте, добавляется таблица `job` со статусом и воркер в том же
процессе. Брокер имеет смысл, когда воркеров станет больше одного и они разъедутся
по разным сервисам.

## 6. Отказоустойчивость

| Отказ | Поведение |
|---|---|
| Эмбеддинг-сервис недоступен | Поиск деградирует до полнотекстового канала, пользователю сообщается о снижении точности |
| LLM недоступна | Список услуг приходит с шаблонным текстом, сценарий не прерывается |
| TZ Generator недоступен | Диалог продолжается без панели готовности |
| MinIO недоступен | Документ фиксируется в БД, файл пересобирается из `payload` при скачивании |
| Обрыв соединения в середине хода | Ход дописывается в БД независимо от соединения, клиент добирает события по `seq` |
| Повторная отправка | `Idempotency-Key` возвращает результат первого хода |
| Параллельный ход в одной сессии | `409 Conflict` с идентификатором активного хода |
